## 2026.09.01.0956

- Fixed the navbar search button opening an empty overlay on any page that already renders a Search Box widget in its content. Reported for citydesk.santa-ana.gov, where the front page (post 3186) carries a `proud_search_box` widget in a SiteOrigin row: clicking the toolbar search icon slid the overlay panel in with nothing inside it, while interior pages worked correctly. Root cause is a setting that was computed and shipped but never read. `proud_seach_print_search()` only calls `the_widget('SearchBox')` when `$GLOBALS['proud_search_box_rendered']` is false (`wp-proud-search.php:215`), so on a page whose content already printed the box the `#overlay-search` container is left empty by design — duplicating it would put a second `#proud-search-input` and a second Angular `searchBoxController` on the page. `init_widgets()` reports which way that went to the front end as `proud_search_box.global.render_in_overlay` (`wp-proud-search.php:210`), but the `proudNavClick` handler in `includes/js/wp-proud-search.js` ignored it and unconditionally called `event.callback(true, false, false, false, …)`, which is `proud-navbar.js`'s open-the-layer path (`wp-proud-core/modules/proud-navbar/assets/js/proud-navbar.js:97`). The sibling plugin already had the missing branch: `proud-actions-app.js:28` reads its own `proud_actions_app.global.render_in_overlay` and, when the app is already on the page, calls `event.callback(false, useId, 0, ['menu', 'search'])` to scroll to the in-page instance rather than open an overlay. Fix: mirrored that shape here. When `render_in_overlay` is true the previous behavior is unchanged, including the `search-active`/`search-active-lite` guard before focusing, since the class is what proves the overlay actually opened. When it is false the handler calls `event.callback(false, 'wrapper-search', 0, ['menu', 'search'], focusSearchInput)` — no overlay, scroll to the in-content form, close the mobile menu and any stale search layer so the box is not hidden behind them, and focus unconditionally, because on that path nothing ever adds `search-active` and the old guard would have suppressed the focus entirely. The focus/caret/`focusout`-rebind block was extracted into `focusSearchInput()` and given a `length` guard, so a page with neither an overlay nor an in-content form degrades to a no-op instead of throwing on `$input[0]`. Scroll targeting is unaffected by the focus call: `proud-navbar.js` computes `$scroll.offset().top` in document coordinates when the callback fires, before the browser's own focus-induced scroll, so the 200ms animation still lands on the right offset. This also fixes a second manifestation of the same bug — the `$('.wrap #wrapper-search')` focus handler calls `Proud.proudNav.triggerOverlay('search')` and so routes through the same switch, meaning clicking into an in-content search box no longer slides a blank panel over the page either. Added the plugin's first test harness: 5 cases in `tests/navbar-search-click.test.js` covering both branches of the flag, the absent-setting fallback, and the two different focus guards, run by Node's built-in `node:test` with zero dependencies via `npm test`. The script is a browser IIFE with no module boundary, so `tests/helpers/harness.js` loads it through `node:vm` against stubbed `jQuery`, `lodash.get`, `Proud` and `angular` globals and hands back the registered behavior; assertions on the `forceClose` array spread it first, since an array built inside the vm realm has a different `Array` prototype and `deepEqual` would otherwise reject an identical list. Mutation-checked: hardcoding the flag back to `true` reproduces the old behavior and fails 3 of the 5 cases. Note for anyone debugging search on a site where the button does nothing at all rather than opening a blank panel — that is a different failure. `includes/js/wp-proud-search.js` is enqueued with a hard dependency on the `proud-actions-app` handle (`lib/search-box.class.php:33`), which is registered by the `wp-proud-actions-app` plugin (`lib/proud-actions-widget.class.php:39`); if that plugin is not installed WordPress silently drops this script from the page, no listener for `proudNavClick` exists, and the click has no effect and logs no error.
