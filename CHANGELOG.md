## 2026.10.07.1016

- Fixed the hero search field opening above the visible area on iOS Safari. Tapping the in-content search box (e.g. the homepage hero on san-rafael-mini-beta-ca) after scrolling down even slightly opened the white overlay with the field out of view, and the user had to scroll up to find it. The toolbar search icon was unaffected and desktop never reproduced it. The two paths differ in when the input gets focus. The toolbar path opens the layer first: `proud-navbar.js` `openLayer` adds `search-active` after 50ms, and only then does the `proudNavClick` callback focus the input, which is already `position: fixed` near the top. The hero path is the reverse. The user's tap focuses the input natively while it is still in normal flow inside the hero, and the class that pins `#wrapper-search` arrives 50ms later. iOS places `position: fixed` against the layout viewport, so a scrolled page (`pageYOffset`) or the keyboard's visual-viewport pan (`visualViewport.offsetTop`) leaves the pinned box above what is on screen. `body.search-active { overflow: hidden }` does not undo either offset.

- Added `resetViewport(force)` to `includes/js/wp-proud-search.js`. It calls `window.scrollTo(0, 0)` when `visualViewport.offsetTop > 0`, or when `force` is set and `pageYOffset > 0`. An `openedFromContent` flag, set by the in-content focus handler and captured then cleared at the top of `case 'search'`, makes the forced reset apply to the hero path only. The toolbar path shares the same callback, and an unconditional reset there would jump a scrolled page to the top behind the overlay. The reset sits inside the existing `search-active` guard because `toggleOverlay` runs the callback twice, once synchronously from `closeLayers` before the class exists and again from `openLayer` after it is added. Only the second call resets. The iOS keyboard pan takes about 250-300ms, which is after the 50ms open, so a `visualViewport` `resize` listener bound in the `.once('proud-search')` block also resets while the overlay is open and `offsetTop > 0`. `offsetTop` is 0 on desktop, so desktop resizes never scroll. Focus is never dropped or re-applied, because iOS only raises the keyboard for a focus inside a user gesture. Scroll position is not restored on close. Esc and the close X go through `proudNav.closeLayers` in wp-proud-core, so restoring there would need a core change. After a hero search the user lands at the top of the page, where the hero is.

- Tests: 9 new cases in `tests/content-focus-viewport.test.js`. They cover the scrolled hero focus, the visual-viewport offset, the twice-run callback, resize while open and while closed, focus at the top, the toolbar path while scrolled, focus kept with no blur, and a browser without `visualViewport`. `tests/helpers/harness.js` gained additive `viewport` options, a `window.scrollTo` recorder, a `visualViewport` stub, `FakeSet.blur` and a `runContentFocus()` helper. Five of the new cases failed before the fix. All 14 pass with `npm test`, and `tests/navbar-search-click.test.js` is unchanged. Chrome and Firefox device emulation do not model the keyboard pan, so this still needs confirming on an iPhone. Use a private tab, because `lib/search-box.class.php` enqueues the script with a `false` version and the URL does not change when the file does.

- Related, shipped in wp-proud-theme: the mobile hamburger (`.navbar-external .menu-button`, `z-index: 1052`) moved to the top-right in #2757 and now covered the overlay close X. It drops to `z-index: 1049` under `.search-active` and `.active-311`.

## 2026.09.01.0956

- Reverted the `proudNavClick` change shipped earlier under this version. It was based on a misreading of the overlay design, broke the search button outright on live, and threw `InternalError: too much recursion` on every click. The change made the handler read `proud_search_box.global.render_in_overlay` and, when the page had already rendered a Search Box widget in its content, call `event.callback(false, 'wrapper-search', 0, ['menu', 'search'], …)` to scroll to the in-content form instead of opening the search layer — on the theory that an empty `#overlay-search` container meant the overlay had nothing to show. That theory is wrong. `#overlay-search` is only the backdrop; the `search-active` class that `proud-navbar.js` adds on the open path is what promotes the form, wherever it sits in the document: `.search-active #wrapper-search { position: fixed !important; z-index: 1051 }` against `.search-active #overlay-search { z-index: 1050; opacity: 1 }` (`wp-proud-core/modules/proud-patternlibrary/css/custom.css:10314` and `:10324`). An empty overlay container on a page carrying its own search box is therefore normal and expected, not a defect. Suppressing the open left the form unpromoted and also removed the only thing terminating a feedback loop: `focusSearchInput()` calls jQuery's `.focus()`, which is `.trigger('focus')` and fires the in-content focus handler regardless of whether the element already held focus; that handler calls `Proud.proudNav.triggerOverlay('search')` unless `search-active` or `search-active-lite` is set, so with the class never applied every click re-entered the same handler until the stack blew. The `search-active` guard was load-bearing and the previous code depended on it without saying so. Restored `includes/js/wp-proud-search.js` to its 2025.10.30.1256 behavior — always `event.callback(true, false, false, false, …)`, focus guarded on the class. Kept the test harness the reverted commit introduced and rewrote its assertions to lock the correct behavior instead: 5 cases in `tests/navbar-search-click.test.js` asserting the layer opens on both values of `render_in_overlay`, that the handler neither scrolls nor force-closes layers, that focus waits for the class, and that the class suppresses the in-content focus re-trigger. Mutation-checked against the reverted commit's own file: it fails 2 of the 5. Run with `npm test` — Node's built-in `node:test`, no dependencies; `tests/helpers/harness.js` loads the browser IIFE through `node:vm` against stubbed `jQuery`, `lodash.get`, `Proud` and `angular` globals. Note that `render_in_overlay` still has no consumer anywhere in the codebase; it is computed at `wp-proud-search.php:210` and read by nothing, which is what made it look like a missing branch in the first place.

- Still outstanding, and not addressed here: on citydesk.santa-ana.gov's front page the promoted form is painted behind the backdrop rather than above it. `#wrapper-search` sits in a SiteOrigin parallax row, and `front-flex.css:15` gives every non-parallax child of `.so-parallax` `position: relative; z-index: 1`, which opens a stacking context on the grid cell. The form's `z-index: 1051` is then resolved inside that cell rather than against the page, so it competes as the cell's `z-index: 1` against a backdrop that is a direct child of `body` at `z-index: 1050`. Interior pages are unaffected because there the form is rendered inside `#overlay-search` itself, at the document root. This is inferred from the CSS and has not been confirmed in a browser.
